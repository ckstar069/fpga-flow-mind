# fpga-flow-mind 项目说明

## 1. 项目定位

`fpga-flow-mind` 是面向 `ai_project_template` 生态业务项目的 FPGA 阶段实现
理解与可视化 Agent。

它读取由 AI Agent 分阶段推进生成的 FPGA 项目代码、RTL、测试、文档、配置和
阶段上下文，通过大模型主导的语义理解与静态证据辅助，生成可追溯的流程图、数
据流图、时序/流水图、公式/信号说明、模块关系视图和不确定项，帮助用户快速理
解当前阶段实际实现了什么。

当前阶段不替用户判断对错，不做 PASS/HOLD，不做自动审计，不修改目标项目。

## 2. 业务场景

业务项目的来源是：

- 模板项目：`/Users/ckstar/Repo/znxt_ofdm/ai_project_template`
- 外部模块来源：`/Users/ckstar/Repo/znxt_ofdm/urban_wireless`

典型业务流程：

```text
使用 ai_project_template 创建业务项目
  -> 从 urban_wireless 导入所需模块
  -> 根据模板中的流程/要求/标准/规范推进开发
  -> AI Agent 从 L0 -> L1 -> ... -> L6 -> RTL 分阶段实现
  -> 产生大量 Python、Verilog、测试、文档和配置变更
  -> 用户无法逐行审核所有 AI 生成代码
  -> 需要工具把真实代码实现转成可理解的图和解释
```

## 3. 当前存在的问题

### 3.1 AI 生成代码过多，用户无法全面审核

AI Agent 的开发产物体量大、跨文件、跨阶段、跨语言。用户很难靠人工通读代码确认
实现方向是否偏离预期。

因此需要桌面端软件帮助用户：

- 分析代码；
- 绘制数据流；
- 绘制输入/处理/输出连线图；
- 解释公式、信号、模块关系；
- 让用户通过看图和证据判断真实代码是否偏离。

### 3.2 项目跨多个开发阶段，且语言会变化

前几个阶段通常是 Python，后续阶段进入 Verilog/RTL，因此工具不能只适配单一语
言或单一目录结构。

### 3.3 临场 Agent 画图效果好，但不可持久化

开发 Agent 因为了解项目上下文、知道阶段目标、读过代码，所以临场画图效果最好。
但这种方式有明显局限：

- 结果不稳定；
- 不能严格做跨阶段对比；
- 不能形成持久语义记忆；
- 不能自然支持后续高级分析、追溯和交互可视化。

## 4. 为什么必须以大模型为主

只通过代码语义分析很难做到准确理解。

静态分析适合做的是：

- 文件/符号/调用提取；
- RTL module/port/signal 提取；
- 测试断言提取；
- 文档和配置读取；
- 行号、切片、交叉引用和 evidence index。

但静态分析很难独立回答：

- 主算法路径是什么；
- 哪些逻辑是主路径，哪些是辅助逻辑；
- Python 阶段概念如何映射到 RTL；
- 当前图中的连接是强证据还是推断；
- 文档、测试和代码不一致时该怎么解释。

因此本项目必须采用：

```text
大模型/Agent = 主力分析者
静态分析/代码语义分析 = 辅助工具与证据基础设施
```

所有主要结论都应绑定源码证据，而不是自由发挥。

## 5. 产品职责

当前阶段产品职责是：

- 尽可能正确理解阶段实现；
- 把结构、数据流和时序关系画出来；
- 把公式、信号、模块关系讲清楚；
- 把跨阶段和跨语言关系组织出来；
- 把证据和不确定项明确展示；
- 支持用户继续追问。

当前阶段不承担：

- 自动正确性判断；
- PASS/HOLD 决策；
- 自动审计结论；
- 自动修改目标项目；
- 运行 Vivado / synthesis / implementation / bitstream。

## 6. MVP 目标

第一个最小可用闭环应聚焦：

```text
单业务项目
  + 单选中阶段
  + 多层理解视图
  + 证据回链
  + 追问能力
```

MVP 至少支持：

1. 打开一个由 `ai_project_template` 创建的真实业务项目；
2. 识别阶段目录和相关上下文；
3. 读取 Python/Verilog/docs/tests/config；
4. 生成至少三类视图：
   - 结构图
   - 数据流图
   - 时序/流水图
5. 每个主要节点或结论可回链到源码证据；
6. 对证据不足处明确标注 `unknown` 或 `inferred`；
7. 支持用户围绕某个图节点继续追问。

## 7. MVP 成功标准

MVP 成功不以“系统替用户裁决”为标准，而以“用户能否更快读懂项目”为标准。

通过条件：

- 用户不需要通读全部代码，也能理解该阶段做了什么；
- 图中有明确输入、处理、中间结果、输出；
- 图不是一堆孤立方块；
- 主要说明有源码证据；
- 不确定项被显式表达；
- Python 阶段与 RTL 阶段都能纳入同一理解框架；
- 结果可持久化并再次打开；
- 用户可以继续提问，而不是只能看一次性报告。

## 8. 非目标

当前阶段明确不做：

- 通用代码库分析器；
- 通用聊天应用；
- 云端优先系统；
- 团队协作平台；
- 审计 dashboard；
- 规则引擎；
- 大而全可视化平台；
- 对目标 FPGA 项目的自动修复或自动改写。
