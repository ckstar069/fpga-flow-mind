# DEVELOPMENT_WORKFLOW.md

本文件定义 `fpga-flow-mind` 的开发与审核协作策略。

## 1. 角色定义

### 实施者

开发人员在本地使用 `claude code + llm` 进行开发实施。

它负责：

- 阅读任务指令；
- 修改文档/代码；
- 运行测试与手工验证；
- 回报修改内容、结果和限制。

### 审核者 / 监督者 / 指导者

开发人员使用以下两种方式之一进行审核与指导：

1. 本地 Codex
2. 网页 GPT

这两种方式是二选一，不要求同时使用。由开发人员根据当前需要切换。

## 2. 两种审核模式

### 模式 A：本地 Codex

适用方式：

- 直接审核本地文件；
- 直接阅读工作区文档和代码；
- 结合开发人员回报进行审查；
- 必要时直接给出下一步实施指令。

在该模式下：

- 不要求每轮都先推送远程才能审核；
- 审核对象可以是本地最新未提交或未推送内容。

### 模式 B：网页 GPT

适用方式：

- 开发人员把本地 Agent 回报带到网页 GPT；
- 网页 GPT 负责审核、监督、规划、指导；
- 网页 GPT 应尽量基于真实仓库内容而不是只相信文字回报。

在该模式下，本地实施者每次任务完成后都必须：

```text
git status
git add ...
git commit -m "..."
git push github main
```

这样网页 GPT 才能看到最新修改并进行有效审核。

## 3. 审核对象

审核不能只看本地 Agent 的文字回报，还应按情况审核：

- 项目文档的新增、删除和修改；
- 产品代码的新增、删除和修改；
- 测试代码和测试结果；
- 架构边界是否漂移；
- 是否出现与需求不一致的实现。

也就是说，审核对象包括：

```text
文字回报
+ 文档 diff
+ 代码 diff
+ 测试结果
+ 手工验证结果
```

## 4. 审核完成后的输出要求

审核完成后，应给出一段可直接发给实施者的下一步指令。

这个指令必须满足：

1. 只输出一个单一可复制代码块；
2. 不混杂解释性段落和多个片段；
3. 不嵌套多层格式；
4. 开发人员可以一次性复制给本地 Agent；
5. 指令中应明确：
   - 任务目标
   - 允许修改范围
   - 禁止事项
   - 验证命令
   - 验收标准
   - 最终回报格式

## 5. 仓库协作约定

- 默认每轮实施完成后必须提交并推送到 `github/main`
- 网页 GPT 审核依赖远程最新内容，实施者必须先 push
- 本地 Codex 可直接审核本地文件，但仍要求实施完成后提交并推送，除非用户明确要求暂不提交/暂不推送
- 本项目 remote 名固定为 `github`，推送命令统一使用：

  ```text
  git push github main
  ```

## 6. 默认审核流程

建议默认流程：

```text
本地实施者完成一轮任务
  -> 回报修改、测试、限制
  -> git status
  -> git add ...
  -> git commit -m "..."
  -> git push github main
  -> 选择审核模式
     -> 本地 Codex：直接看本地文档/代码并审核
     -> 网页 GPT：由网页 GPT 审核远程最新修改
  -> 审核者输出结论
  -> 审核者提供单一代码块形式的下一步指令
  -> 本地实施者继续执行
```

## 7. 项目特定约束

不论使用哪种审核模式，都必须保持以下原则：

- 目标业务项目只读；
- 不修改 `fpga_project_*`；
- 不运行 Vivado；
- 不运行 synthesis / implementation / bitstream；
- 不把产品做成审计器或 PASS/HOLD 工具；
- 大模型是主分析者，静态分析是辅助工具；
- 审核时不仅看“做了什么”，还要看“是否偏离产品目标”。
