# Phase 11 Overview：多阶段语义记忆、测试覆盖图与 agent-scope 联动

---
status: draft
updated: 2026-06-15
---

> 本文档是 Phase 11 的**方向性 overview**。Phase 11 是 Post-MVP 中**探索性最强**的阶段，其详细需求/设计可能在编制时被进一步拆分或重新排序。进入 Phase 11 编码前仍需编制并审核详细文档为 active。Phase 11 当前**未开始编码**。
> 本文中的 **Phase** 指 `fpga-flow-mind` 本项目开发阶段；**L0 / L1 / ... / RTL** 指业务项目实现阶段，不可混用。

## 1. 背景与问题

截至 Phase 10，`fpga-flow-mind` 已经能在单个业务项目内做单阶段与跨阶段理解。但理解产物仍是**一次性、项目内、session 内**的：

- **不复用**：换一个项目、或重开 session，之前的理解无法作为背景知识被复用；
- **历史问答不利用**：Phase 6 已持久化 QA history，但历史问答未作为可利用的语义资产；
- **测试维度缺失**：测试是理解"实现是否被验证"的重要维度，但当前没有把测试与实现的关系组织成覆盖理解；
- **生态孤立**：`PROJECT_BRIEF` §10 提到"与 `agent-scope` 的上下文联动"和"外部开源可视化工具接入"，但当前 `fpga-flow-mind` 独立运行，未与开发生态联动。

`PROJECT_BRIEF` §3.3 指出，开发 Agent 临场画图"不能形成持久语义记忆"。Phase 11 的命题正是补上这一层：**把阶段/跨阶段理解沉淀为可复用的语义记忆，并探索与 agent-scope 上下文、测试覆盖理解、外部可视化工具的联动边界。**

> Phase 11 是 Post-MVP 主干的最后一环，也是**边界探索性最强**的一环。其三个子主题（语义记忆、测试覆盖图、联动）既相互关联，也可能在详细规划时被拆为独立子阶段。

## 2. 阶段目标

1. **多阶段语义记忆**：把跨阶段理解产物（Phase 10）沉淀为可复用的语义记忆，使其能在重开 session、相关项目、后续分析中被作为背景知识引用，而非每次从零开始。
2. **历史问答利用**：把已持久化的 QA history（Phase 6）从"仅持久化"提升为"可利用的语义资产"——例如复用历史问答、避免重复追问、为新问题提供背景。
3. **测试覆盖理解**：把测试与实现的关系组织为覆盖理解（哪些实现被测试覆盖、哪些未覆盖、覆盖以何种方式），作为理解"实现是否被验证"的维度，**不做覆盖率裁决**。
4. **agent-scope 上下文联动**：探索与 `agent-scope`（开发 Agent 的上下文/作用域体系）的联动边界——例如把 `fpga-flow-mind` 的理解产物作为 agent-scope 的上下文输入，或反之。
5. **外部可视化工具接入边界**：探索与外部开源可视化工具的接入边界（数据导出、对接格式、单向 vs 双向），明确哪些可以接入、哪些超出边界。

> 4、5 两项是**探索性**的，目标是明确"联动/接入的可行边界与最小可行形态"，而非一次性建成完整集成。

## 3. 用户价值

- 用户的理解积累不丢失：跨 session/项目复用语义记忆，理解越用越深，而非每次从零；
- 历史追问被利用，减少重复提问，提升问答效率与连贯性；
- 用户能理解"实现的哪些部分被测试覆盖、哪些没有"，作为判断实现成熟度的一个维度（仍由用户自行判断，不裁决）；
- 与开发生态（agent-scope、外部可视化工具）联动，让 `fpga-flow-mind` 嵌入 AI 开发流程而非孤立运行。

## 4. 允许范围

Phase 11 允许做（具体范围在详细文档中收敛，且可能拆分为子阶段）：

- 新增多阶段语义记忆模型与存储（构建于 Phase 10 跨阶段产物之上）；
- 提升 QA history 的利用能力（复用、背景化）；
- 新增测试覆盖理解模型（测试 ↔ 实现 关系组织，描述性而非裁决性）；
- 探索 agent-scope 联动的最小可行形态与数据/上下文边界；
- 探索外部可视化工具接入的最小可行形态（导出格式、单向对接优先）；
- 配套测试与回归。

## 5. 明确非目标

Phase 11 **不做**：

- **不做团队协作平台 / 审批流 / 多人分享**（`product-scope.md` 非目标）；
- **不做审计 dashboard**（不把理解产物做成监控/审计看板）；
- **不做自动修复 / 自动改写目标项目**（不修改目标 FPGA 项目）；
- **不做正确性裁决 / PASS/HOLD**（测试覆盖理解是描述性的，不裁决"覆盖够不够/对不对"）；
- **不做 server-first / cloud-first 的记忆共享**（记忆仍以本地为主，云端共享超出边界）；
- **不修改目标业务项目**，不运行工具链；
- **不脱离 grounding**：语义记忆、测试覆盖理解、联动产出的结论同样必须可回链证据。

## 6. 与前后阶段关系

- **前置**：Phase 10（跨阶段理解）。语义记忆的"来源"是 Phase 10 的跨阶段理解产物；没有跨阶段理解，就没有可沉淀的多阶段语义记忆。同时依赖 Phase 9（真实 LLM）支撑记忆的归纳与复用。详见 [`post-mvp-roadmap.md`](post-mvp-roadmap.md) §4。
- **后置**：Phase 11 是 Post-MVP 主干（Phase 7 → 9 → 10 → 11）的终点。其产出的"记忆 + 联动"形态将定义 `fpga-flow-mind` 进入 v1.x 之后的演化方向，但本轮不承诺 v1.x 路线。
- Phase 11 的三个子主题在内部可能有依赖（如测试覆盖理解可复用语义记忆能力），详细规划时需排序。

## 8. 验收方向（方向性，具体门槛在需求/测试文档中量化）

- 语义记忆可在重开 session/相关项目场景下被复用，复用结论可回链证据；
- QA history 被利用（如复用、背景化），而非仅持久化；
- 测试覆盖理解能组织测试↔实现关系，描述性表达覆盖情况，不裁决；
- agent-scope 联动与外部工具接入有明确的最小可行形态与边界文档（即便只完成最小形态）；
- 既有能力（单阶段、跨阶段、Q&A、持久化）不发生回归；
- 真实桌面验收通过，安全/隐私边界保持，全量构建/测试通过。

## 9. 风险与边界

- **范围过大风险**：三个子主题 + 联动探索，极易失控。详细规划必须拆分子阶段、设最小可行形态，避免"什么都做一点、什么都没做完"。
- **隐私/安全风险**：语义记忆可能跨项目携带信息，须防止把一个项目的敏感理解泄露到另一个项目的展示中；记忆存储与边界须显式设计。
- **越界裁决风险**：测试覆盖理解最易滑向"覆盖率是否达标"的裁决。必须保持描述性。
- **联动依赖风险**：agent-scope 与外部工具的接入依赖外部系统的形态与稳定性；须以"最小可行 + 边界明确"为先，避免深度耦合不可控的外部系统。
- **定位漂移风险**：联动探索容易把产品带向"协作平台 / dashboard / 大集成平台"。每步都须回到 `product-scope.md` 非目标复查。
- **安全边界**：记忆/联动若涉及外发（如导出给外部工具、共享给 agent-scope），须沿用 Phase 9 的受控与审计原则；不修改目标项目，不运行工具链。
