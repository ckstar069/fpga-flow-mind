# Phase 8 Overview：产品级 UI/UX 工作台重构

---
status: draft
updated: 2026-06-15
---

> 本文档是 Phase 8 的**方向性 overview**。详细 UI/UX 设计、需求、测试设计与编码计划在进入 Phase 8 编码前另行编制并审核为 active。Phase 8 当前**未开始编码**。

## 1. 背景与问题

当前 UI 在 MVP 阶段为**工程调试式界面**：它的首要目标是让开发者验证"证据→理解→视图→trace→Q&A→持久化"链路打通，而非让最终用户高效理解项目。这导致若干可用性问题：

- **信息架构偏调试**：面板按后端能力划分（evidence panel / trace panel / view panel / QA panel），而非按用户"理解一个阶段"的认知流程组织；
- **阶段工作流不连贯**：收集证据、生成理解、生成视图是分散的步骤触发，用户需手动串联，缺乏"理解一个阶段"的一体化引导；
- **证据 / trace / Q&A 组织零散**：用户难以在同一上下文中"看图→点节点→读证据→追问"形成闭环；
- **最近项目与 session 体验单薄**：列表、空状态、加载/错误恢复提示偏功能实现，缺少产品级体验；
- **空状态 / 错误状态不完整**：`source_changed` / `source_missing` / `stage_empty` 等状态有横幅提示但体验粗糙；
- **视觉层级薄弱**：confirmed / supported / inferred / unknown / conflicting 的视觉语义、证据强度、不确定项未被层级化表达。

这些问题不影响技术闭环成立，但影响"用户能否真正更快读懂项目"——而这正是 `product-scope.md` 定义的成功标准。Phase 8 把界面从"能用"重构为"好用"。

## 2. 阶段目标

1. **重构信息架构**：以"理解一个阶段"的用户认知流程为主线，重新组织面板与导航。
2. **连贯阶段工作流**：把证据收集 → 理解生成 → 视图生成 → trace 回链 → 追问整合为顺滑的单阶段理解流，减少手动串联。
3. **整合证据 / trace / Q&A 上下文**：在同一上下文中完成"看图→点节点→读证据→追问"闭环。
4. **产品化 session 体验**：最近项目、session 列表、空状态、加载/错误恢复达到产品级可用度。
5. **补全空状态 / 错误状态**：对 `source_changed` / `source_missing` / `source_path_not_allowed` / 空阶段 / 命名异常阶段等给出清晰、可操作的 UI 反馈。
6. **建立视觉层级**：用视觉语义表达 confidence（confirmed/supported/inferred/unknown/conflicting）、证据强度、不确定项与证据缺口。

## 3. 用户价值

- 用户打开项目后，被自然引导完成"理解一个阶段"，而不是面对一堆调试面板自己拼流程；
- 用户在同一上下文中看图、查证据、追问，理解效率显著提升；
- 用户能一眼区分"哪些是强证据结论、哪些是推断、哪些是未知"，不被高置信度的推断误导；
- session / 最近项目 / 错误恢复体验达到真实可用，降低使用摩擦。

## 4. 允许范围

Phase 8 允许做（具体范围在详细文档中收敛）：

- 重构前端信息架构、导航、面板组织与阶段工作流编排；
- 重构 session / 最近项目 / 空状态 / 错误状态的前端体验；
- 建立并应用 confidence / 证据强度 / unknown 的视觉语义系统；
- 为支撑新信息架构，做**必要的前端状态结构调整**（如集中 active view type、UI state 恢复增强）；
- 配套调整 Tauri command 的**展示性**返回结构（仅当不改语义、不破坏既有契约时）。

> Phase 8 是**前端为主的阶段**。后端改动应限于"支撑新 UI 所需的最小展示性调整"，不得借机改变语义模型或分析能力。

## 5. 明确非目标

Phase 8 **不做**：

- **不改变核心语义模型**：`ImplementationUnderstanding`、evidence model、`confidence` 枚举、trace 模型的字段语义与契约保持不变（视觉表达改变 ≠ 模型改变）；
- **不扩大分析能力范围**：不接真实 LLM（Phase 9）、不做跨阶段映射（Phase 10）、不做语义记忆（Phase 11）；
- **不引入新的重前端依赖导致偏离技术栈**：仍为 Tauri + React/TypeScript，视图仍用纯 SVG + CSS（沿用 Phase 4 约束，不引入 React Flow / D3 / Mermaid，除非详细文档明确论证并审核）；
- **不改变安全边界**：目标项目只读、持久化只写 app-owned storage 等约束不变；
- **不追求"大而全可视化平台"**（`product-scope.md` 非目标），仍聚焦三类核心视图 + 证据 + Q&A 的可用化。

## 6. 与前后阶段关系

- **前置/并行**：可与 Phase 7 部分并行，但工作台的**信息架构宜在 Phase 7 暴露真实理解形态后定型**，因此更稳妥是 Phase 7 完成或接近完成时启动（见 [`post-mvp-roadmap.md`](post-mvp-roadmap.md) §4）。
- **后置**：Phase 8 的视觉语义系统（confidence/unknown 表达）会被 Phase 9 真实 LLM 的 grounding 结果直接复用——真实 LLM 会带来更多 inferred/unknown/citation，需要一个成熟的视觉层级来承载。
- Phase 8 与 Phase 9/10/11 在语义层无强依赖，可相对独立推进，但产物（工作台形态）是后续阶段能力落地的承载界面。

## 8. 验收方向（方向性，具体门槛在需求/测试文档中量化）

- 真实用户（或代表用户的验收者）能无需说明完成"打开项目→选阶段→理解→查证据→追问"全流程；
- 信息架构以"理解一个阶段"为主线，面板不再按后端能力机械划分；
- confidence / 证据强度 / unknown / evidence_gap 有清晰且一致的视觉表达；
- session / 最近项目 / 空状态 / 错误状态达到产品级可用度；
- 既有能力（三类视图、trace 回链、Q&A、持久化）不发生回归；
- 真实桌面验收通过，安全边界保持，全量构建/测试通过。

## 9. 风险与边界

- **形式重于内容风险**：UI 重构容易沦为"更好看的调试面板"。验收必须回到 `product-scope.md` 成功标准——"用户能否更快读懂项目"，而非"面板是否更漂亮"。
- **借机改后端风险**：前端阶段最容易顺手改语义模型/分析能力。必须严守"仅展示性调整、不破坏契约"。
- **依赖蔓延风险**：引入重可视化库会偏离技术栈约束，需在详细文档中论证或拒绝。
- **回归风险**：UI 大重构可能破坏 Phase 4/5/6 已验收的视图/trace/Q&A/持久化能力，需完整回归验收。
- **可访问性/多平台**：macOS / Linux 视觉与交互一致性需在验收中覆盖。
