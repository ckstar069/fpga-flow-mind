# Phase 10 Overview：跨阶段理解与 Python-to-RTL 映射

---
status: draft
updated: 2026-06-15
---

> 本文档是 Phase 10 的**方向性 overview**。详细需求、设计、测试设计与编码计划在进入 Phase 10 编码前另行编制并审核为 active。Phase 10 当前**未开始编码**。
> 本文中的 **Phase** 指 `fpga-flow-mind` 本项目的开发阶段；**L0 / L1 / ... / RTL** 指被分析业务项目的实现阶段，二者不可混用。

## 1. 背景与问题

`ai_project_template` 业务项目的本质特征是**跨阶段、跨语言推进**：前期阶段（L0/L1/...）多为 Python，后期进入 Verilog/RTL。`PROJECT_BRIEF` §3.2 把"项目跨多个开发阶段，且语言会变化"列为核心问题之一，§10 把"Python 到 RTL 映射图"列为关键后续方向。

但截至 Phase 9，`fpga-flow-mind` 的理解能力是**单阶段孤立**的：

- 每个阶段独立收集证据、独立生成 `ImplementationUnderstanding`；
- 阶段之间没有"接口约定"的显式组织；
- Python 阶段的算法概念与 RTL 阶段的硬件实现之间没有语义映射；
- 用户无法回答"RTL 里的这个模块，对应 Python 里的哪段算法？二者的处理步骤是否一致？哪里出现了偏差或缺口？"

这正是用户最深层的理解需求之一——确认"AI Agent 从 Python 推进到 RTL 的过程中，实现方向是否一致"。Phase 10 的命题是：**把 L0/L1/.../RTL 的实现关系组织起来，支持跨阶段对比与 Python 到 RTL 的语义映射，让用户能看清"从算法到硬件"的演化与缺口。**

## 2. 阶段目标

1. **阶段间接口组织**：把上游阶段对下游阶段的接口约定（输入/输出、数据结构、约定文件）显式组织为跨阶段关系，而非散落在各阶段 understanding 中。
2. **跨阶段符号映射**：建立 Python 阶段概念/符号与 RTL 阶段模块/端口/信号之间的可追溯映射关系。
3. **算法到 RTL 的语义映射**：把 Python 算法处理步骤与 RTL 实现的处理步骤对照，表达"哪些算法步骤被实现、如何实现"。
4. **差异与缺口表达**：当 Python 算法与 RTL 实现出现不一致、缺失、新增时，以 evidence 约束的方式表达差异/缺口，**不裁决对错**。
5. **跨阶段 trace**：用户可从一个阶段的节点/claim 追溯到另一阶段的相关实现与证据。

> Phase 10 的语义映射**在实质上依赖真实 LLM**（Phase 9）——Python 概念到 RTL 硬件的归纳是静态分析无法独立完成的。同时依赖 Phase 7 对真实多阶段项目的单阶段理解质量。

## 3. 用户价值

- 用户能看清"从 Python 算法到 RTL 硬件"的完整演化路径，而非孤立的阶段视图；
- 用户能回答"RTL 实现是否忠实于 Python 算法意图"——通过 evidence 约束的映射与差异表达自行判断，而非由工具裁决；
- 用户能跨阶段追溯：从 Python 的某段算法定位到对应的 RTL 模块与证据，反之亦然；
- 这是 `fpga-flow-mind` 区别于"单阶段代码浏览器"的核心价值落点。

## 4. 允许范围

Phase 10 允许做（具体范围在详细文档中收敛）：

- 新增跨阶段关系模型（阶段间接口、符号映射、算法-RTL 映射、差异/缺口）；
- 在既有单阶段 understanding 之上，构建跨阶段 understanding 层（不破坏单阶段模型与契约）；
- 利用 Phase 9 的真实 LLM 做跨语言语义归纳与映射；
- 新增跨阶段视图/对比视图（前端），承载映射、差异与跨阶段 trace；
- 配套测试与回归（含跨阶段 trace 准确性、映射 grounding）。

## 5. 明确非目标

Phase 10 **不做**：

- **不做正确性裁决**：不判断 Python 算法与 RTL 实现"谁对谁错"，只表达差异/缺口，判断权留给用户；
- **不运行综合 / 形式验证 / 仿真**：不跑 synthesis / implementation / bitstream，不做 RTL 等价性形式验证；
- **不做 PASS/HOLD / 审计结论**；
- **不做多阶段语义记忆沉淀**（属于 Phase 11）——Phase 10 产出的是"当前项目的跨阶段理解"，而非跨 session 的可复用记忆；
- **不修改目标业务项目**；
- **不脱离 grounding**：跨阶段映射的每个关系同样必须可回链证据，差异/缺口表达遵循 unknown/evidence_gap 语义，不编造。

## 6. 与前后阶段关系

- **前置**：Phase 7（真实多阶段项目的单阶段理解质量）+ Phase 9（真实 LLM 语义引擎）。跨阶段 Python→RTL 映射在实质上依赖真实 LLM，且需要真实多阶段项目作为对象。详见 [`post-mvp-roadmap.md`](post-mvp-roadmap.md) §4。
- **后置依赖方**：Phase 11（多阶段语义记忆）的"记忆来源"正是 Phase 10 的跨阶段理解产物——没有跨阶段理解，就没有可沉淀的多阶段语义记忆。
- Phase 10 是 Post-MVP 主干（Phase 7 → 9 → 10 → 11）的第三环，也是项目核心价值（跨阶段/跨语言理解）的落点。

## 8. 验收方向（方向性，具体门槛在需求/测试文档中量化）

- 真实多阶段业务项目上，能组织阶段间接口、生成 Python→RTL 符号/算法映射；
- 跨阶段映射的每个关系可回链证据，伪造映射被拒绝或标注为推断/unknown；
- 差异/缺口被诚实表达，不裁决对错；
- 用户可跨阶段 trace（Python 算法 ↔ RTL 实现），trace 准确回链；
- 单阶段理解能力不发生回归；
- 真实桌面验收通过，安全边界保持，全量构建/测试通过。

## 9. 风险与边界

- **越界裁决风险**：跨阶段对比最易滑向"判断 RTL 是否正确实现 Python 算法"。必须严守"只表达差异/缺口、不裁决"，差异的语义是描述性的而非判定性的。
- **映射幻觉风险**：Python→RTL 映射是 LLM 最容易幻觉的场景。grounding 必须强制每个映射关系回链两端证据，无法回链的降级为 inferred/unknown。
- **模型膨胀风险**：跨阶段模型若设计不当易与单阶段模型耦合过深，破坏既有契约；需保持"跨阶段层构建于单阶段层之上、不侵入单阶段"。
- **复杂度风险**：跨阶段视图易变成"大而全可视化平台"（`product-scope.md` 非目标）；需聚焦"映射 + 差异 + trace"，克制新增图类型。
- **安全边界**：跨阶段归纳需要更多上下文外发（若启用真实 LLM），须沿用 Phase 9 的受控上下文与审计；不修改目标项目，不运行工具链。
